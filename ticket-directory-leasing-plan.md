## Objective

Each Ticket executes in an execution directory for which it holds a directory lease. The main Session selects an execution directory pool, a named configuration that supplies execution directories under one of two Executor-managed allocation policies:

- **Fixed inventory:** an operator-configured pool lists execution directory IDs and paths. For a Ticket without directory affinity, the Executor selects the least recently used directory eligible for lease acquisition.
- **Per-Ticket creation:** the built-in pool with reserved ID `default` always creates a fresh, dedicated execution directory for each Ticket at its first launch. The Executor reserves a new path beneath the default-pool root, then creates and prepares it; it never selects an existing directory for reuse. Fixed-inventory eligibility rules, including external Session occupancy and Git-cleanliness gates, do not apply to this pool. This pool configuration always exists, even with no operator-configured pools; the directories themselves are created on demand. Retries, restart recovery, and resumption retain the committed directory rather than creating another one.

The operator defines additional pools and pool-selection instructions. The main Session selects a matching operator-configured pool, or selects `default` when no other pool is selected under those instructions. The placement target is a pool ID; the reason and context version are decision metadata, not a choice of allocation policy or execution directory. The Engine records the pool placement at acceptance. The Executor separately manages directory eligibility, worker-slot admission, directory reservations and leases, workspace preparation, and execution. Workers cannot choose or change pool placement.

## Terminology

Use these terms consistently in code, tool descriptions, prompts, panel labels, and documentation. Short forms `pool`, `directory`, and `lease` refer to the defined execution-directory concepts below, never to a worker pool, a worker slot, or an arbitrary filesystem path.

| Term | Precise meaning |
| --- | --- |
| Execution directory pool (`DirectoryPool`) | A named placement target with an allocation policy. It is configuration, not a filesystem directory or a collection of workers. |
| Allocation policy | How a pool supplies execution directories: fixed inventory (`allocation.kind: 'fixed'`) or per-Ticket creation (`allocation.kind: 'per-ticket'`). |
| Execution directory | The concrete filesystem directory in which a Ticket works. A directory record identifies its stable `directoryId` and canonical `path`; that record may be reserved before the filesystem directory exists. |
| Workspace contents | The checkout, branch state, and artifacts inside an execution directory. They may belong to different Tickets at different times without changing the directory's identity. |
| Pool placement (`PoolPlacement`) | The acceptance-time decision `{ poolId, reason, contextVersion }`. It selects a pool, not a directory or a worker slot. |
| Directory reservation | The atomic commit of a directory ID/path and an unreleased directory lease. A Ticket's first reservation also fixes its directory affinity. Reservation performs no filesystem creation or preparation. |
| Directory lease (`DirectoryLease`) | A Ticket's exclusive ownership of an execution directory from committed reservation through safe release. Reserved, preparing, active, and releasing leases all exclude other owners. |
| Directory affinity (`TicketDirectoryAffinity`) | The permanent pool ID, directory ID, and canonical path to which a Ticket must return. It survives lease release and does not itself grant current ownership. |
| Git working-tree resource | The resolved canonical working-tree root, verified against its worktree-specific Git metadata. It is an additional exclusive resource claimed by a directory lease across all pools. Sibling execution directories inside one working tree share this resource; distinct linked worktrees do not, even when they share a common Git directory. |
| External Session occupancy | Use of the same or an overlapping canonical workspace, or the same resolved Git working-tree resource, by a Session other than the requesting Ticket's verified Executor Session and authorized descendants. For fixed-inventory directories, it blocks use when that Session is running, currently open in a user client view, or owns outstanding background activity. It is not an eligibility gate for `default`. |
| Git-clean workspace | A Git working tree with no staged, unstaged, untracked, or conflicted changes, including dirty submodule state, and no unfinished Git operation. Repository identity and status must be verified; an unreadable or failed check is not evidence of cleanliness. Ignored files alone do not count as Git changes, but still require ordinary artifact/recycling checks. Cleanliness is a fixed-inventory reuse gate, not a default-pool allocation rule. |
| Directory eligible for lease acquisition | A fixed-inventory directory that satisfies the request's pool/affinity constraints, has no conflicting unreleased directory lease, Git working-tree claim, or recovery fence, is verified free of external Session occupancy, is Git-clean if it belongs to a Git working tree, and meets the applicable identity, filesystem, and recycling checks. Unknown occupancy or Git status is not eligible. Eligibility does not imply preparation for the requesting Ticket. `default` uses fresh-directory creation instead of this candidate filter. |
| Worker-slot availability | The scheduler's ability to admit a launch or worker turn. Independent of directory eligibility; a Ticket can hold a lease without holding a worker slot. |
| Default-pool root | The configured execution-root path used only to resolve first reservations in `default`. It is not the parent of every fixed-inventory directory. |

Use **newly accepted Ticket** for acceptance and **Ticket without directory affinity** for first-reservation logic; an ended Ticket may resume without ever having reserved a directory. Use **open/ended Ticket**, **pending/running/ended Assignment**, and the explicit lease state rather than the ambiguous phrase “active work.” An `active` lease means ownership with preparation complete, not that a worker is currently running; recovery clearance is an independent requirement.

Use explicit verbs: **select a pool → reserve a directory/acquire its lease → create the directory if needed → prepare workspace contents → execute → stop activity → recycle workspace contents → release the directory lease**. Freeing a worker slot, releasing a lease, and deleting a filesystem directory are different operations. In this plan, directory allocation means selection plus reservation, not filesystem creation. Report directory eligibility and worker-slot availability separately rather than calling either one simply “capacity.”

## Component responsibilities

Use the existing components from the [architecture](<docs/007-architecture.md>), not a generic additional actor:

| Component | Responsibility in this plan |
| --- | --- |
| Main Session | Reads placement instructions and selects a pool as part of acceptance |
| Engine | Validates acceptance and pool selection, creates the Ticket with its placement, and queues execution in one transaction |
| Store | Persists Tickets, pool selections, queue order, and leases; enforces allocation uniqueness constraints |
| Effects | Persists queued work and dispatches it to registered handlers after commit |
| Executor | Manages directory eligibility, worker-slot admission, and directory leases through its proposed directory manager; creates execution directories as needed, prepares workspace contents, starts Assignments, and releases directory leases safely |
| Sessions | Creates or resolves Executor Sessions and delivers assignment messages using DeepSeek Harness services |
| Runtime | Constructs and wires the components and coordinates startup/shutdown; does not make placement decisions |

The directory manager is an implementation helper owned by the Executor, not a new agent or a replacement for the Engine. DeepSeek Harness supplies the underlying Session and subprocess services.

## Design decisions

1. Choose placement as part of acceptance, not in a separate dispatch step. The main Session includes placement in `orchestrator_route` items with `kind: 'accept'` and in `orchestrator_eval_decide` results with `decision: 'accept'`. The Engine atomically creates the authorized Ticket, records placement through the Store, and enqueues execution through Effects. There is no separate dispatch tool or normal awaiting-placement phase.
2. The main Session receives Ticket requirements, operator-authored pool-selection rules, pool IDs/descriptions, and an opaque placement-context version to echo on acceptance. Its placement context excludes directory IDs/paths, current owners, directory eligibility or inventory counts, worker-slot availability or limits, and queue lengths. Pool placement depends on semantic requirements, not those scheduling metrics.
3. The placement target is an execution directory pool ID, including `default`; `reason` and `contextVersion` are decision metadata. Placement never chooses an individual execution directory, arbitrary path, or separate new-directory option. The Executor applies the selected pool's allocation policy.
4. Having no directory eligible for lease acquisition in a fixed-inventory pool is not a pool-placement failure. The Ticket stays queued for that pool until a directory is eligible and a worker slot is available. Changes in directory eligibility or worker-slot availability do not trigger reconsideration by the main Session, pool switching, or fallback to `default`.
5. The default-pool root backs the built-in `default` pool. When no operator-configured pool is selected under the placement instructions, the main Session records `placement.poolId: 'default'` in the acceptance decision. The Executor reserves a fresh Ticket-specific path using the existing naming scheme, with collision disambiguation before reservation, then creates and prepares the execution directory. Do not apply fixed-inventory eligibility rules to `default`, including Session occupancy or Git-cleanliness checks on the root, ancestors, or dedicated directory. In particular, the main Session running or displayed at the state directory must not block default-pool work beneath that directory. Authorization, worker-slot admission, exclusive resource ownership, filesystem correctness, and crash-recovery safeguards still apply; this exemption is not permission to overwrite an existing path or share a Git working tree. This semantic default does not depend on directory eligibility or worker-slot availability in another pool.
6. Once acquired, a directory lease belongs to a Ticket, not an Assignment or worker slot. It remains held while the Ticket is open, including waiting, review, blocked, failed, retries, and runtime restarts. A newly accepted Ticket waiting for its first directory reservation has pool placement but no directory lease yet.
7. Ticket termination begins asynchronous shutdown, preservation, any required workspace recycling, and atomic directory-lease/Git-resource release. Ownership remains held until activity has stopped and the applicable preservation/recycling contract has succeeded. Fixed inventory must be ready for reuse; `default` preserves its dedicated contents without reuse eligibility gates. Lease release does not mean deleting the filesystem directory.
8. Runtime shutdown does not release leases. Ownership and queued pool selections survive restart. Recovery fences every unreleased lease, including active leases, until previous execution is proven quiescent. Lost process handles, an empty DSH job registry, elapsed time, and host-process death are not proof. Uncertain directories remain quarantined against preparation, execution, recycling, and release until verified cleanup or operator remediation establishes that proof.
9. After its first directory reservation, a Ticket keeps its original pool, directory ID, and canonical path as durable affinity, even after its lease is released. When an ended Ticket resumes, the Executor must reacquire that exact directory; if it is leased or still releasing, the Ticket waits for it even if other directories are available. There is no new main-Session placement decision, LRU reselection, directory substitution, or preemption. Existing authorization and human-stop rules for resumption remain unchanged; the checkout must be restored safely after intervening use.
10. Ticket short names remain branch identifiers; they no longer necessarily match directory basenames.
11. Leases coordinate cooperative execution. They are not an OS security boundary for workers with unrestricted filesystem access.
12. LRU applies only to a Ticket's first directory reservation in a fixed-inventory pool and ranks directories eligible for lease acquisition by their last committed lease-acquisition sequence. Never-used directories rank first, with stable directory-ID tie-breaking. Every successful acquisition, including resumption, updates this sequence atomically with reservation; failed reservations and releases do not update it. Directory affinity survives independently of the current lease.
13. Acceptance is bound to the exact versioned placement context supplied to the main Session. A new acceptance with a stale or unknown context version is refused atomically; it never silently records the current instruction version for an older decision. Already accepted requests return their original Ticket, placement, and versions before current-context validation.
14. For newly accepted Tickets, acceptance records the short name, assignment text, and pool placement, not a directory pathname. Resolve the pathname only at launch admission when a worker slot is available: select an eligible fixed-inventory directory, or reserve a fresh path for `default`. Persist affinity, the lease, required Git working-tree claims, and preparation intent before creating the directory or preparing its workspace contents after commit. A committed reservation fixes the path even if a crash precedes directory creation. Track allocation and preparation separately; a pathname alone proves neither prior creation nor successful preparation.

15. A fixed-inventory directory with external Session occupancy is unusable by the superagent even without a superagent lease. An unrelated Session blocks it while running **or** while any user has that Session open in a client view, including an idle Session. Existing Session records, loaded-but-idle agents, and sidebar/history entries alone do not mean the user has the Session open. Apply this exclusion to fixed-inventory first reservations, exact-directory resumption, preparation, execution, and workspace recycling. Never stop or close an unrelated Session automatically to obtain a directory; wait without changing the accepted pool or affinity. Do not apply this gate to `default`.

16. A fixed-inventory directory belonging to a Git working tree is ineligible for a new lease while that working tree is not clean. Apply this to first reservations and reacquisition after lease release, including pinned-directory resumptions. Do not apply the clean-for-reuse gate to dedicated `default` directories, which are never reassigned to another Ticket. Do not clean, stash, commit, or discard pre-existing changes merely to make a directory eligible. Changes produced by the Ticket during its own unreleased lease are expected and do not revoke that lease or block ordinary continuation/retries; cleanliness is a shared-directory acquisition/reuse boundary, not a rule forbidding implementation edits.

17. The resolved Git working-tree root is an exclusive resource in addition to the execution directory. Acquire its claim atomically with a directory lease, retain it through preparation, waiting, execution, recovery, and recycling, and release it only with safe lease release. This applies across pool boundaries and to subdirectories of the same working tree: two sibling paths must not execute concurrently merely because their directory paths do not overlap. Distinct linked worktrees may execute independently; the common Git directory is not the exclusivity key. Default-pool preparation creates an independent checkout/worktree at its fresh path rather than borrowing an ancestor's working tree.

## Proposed contracts

```ts
// Execution settings; only IDs/descriptions appear in placement context.
// The default entry is synthesized from the execution-root setting and its persisted description.
type DirectoryPool =
  | {
      id: 'default';
      description: string;
      allocation: { kind: 'per-ticket'; root: string };
    }
  | {
      id: string; // Operator-configured IDs must not be 'default'.
      description: string;
      allocation: {
        kind: 'fixed';
        directories: { id: string; path: string }[];
      };
    };

// One acceptance-time placement decision; all fields are required.
interface PoolPlacement {
  poolId: string; // Includes the built-in 'default' pool.
  reason: string;
  contextVersion: string; // Copy PlacementContext.version from the context read.
}

// Bounded semantic resource; the server retains each snapshot and its instruction revision.
interface PlacementContext {
  version: string; // Opaque revision of instructions plus selectable pool IDs/descriptions.
  instructions: string;
  pools: { id: string; description: string }[];
}

// One additional field on both existing acceptance schemas, not a new tool.
// Placement metadata stays inside this object; no directory choice or scheduling metrics.
interface AcceptancePlacementFields {
  placement: PoolPlacement;
}

// Executor-managed allocation, not part of the main Session's placement decision.
interface DirectoryLease {
  id: string;
  directoryId: string;
  ticketId: string;
  poolId: string; // Required for every lease, including 'default'.
  path: string;
  state: 'reserved' | 'preparing' | 'active' | 'releasing';
  executionEpoch: string; // Durable Runtime incarnation associated with managed activity.
  recovery: 'cleared' | 'required' | 'quarantined'; // Fence independent of lease lifecycle state.
}

// An additional durable exclusive claim, subordinate to an unreleased directory lease.
// A fresh checkout reserves its intended root before creation; preparation verifies it.
interface GitWorktreeClaim {
  leaseId: string;
  root: string; // Canonical working-tree root; unique among unreleased claims.
  gitDirectory?: string; // Canonical worktree-specific metadata, not the shared common dir.
  state: 'reserved' | 'verified';
}

// Persisted on the Ticket at its first directory reservation; not cleared on release.
interface TicketDirectoryAffinity {
  poolId: string;
  directoryId: string;
  path: string;
}

// Allocation metadata in Store; not included in main-Session placement context.
interface DirectoryUsage {
  directoryId: string;
  lastLeaseSequence: number; // Zero if never leased; otherwise a durable increasing sequence.
}
```

These are minimum contracts, not final database schemas. Persist the placement explanation, supplied placement-context version and its corresponding instruction revision/snapshot, queue order, preparation intent/start/completion, failures, timestamps, and released lease history as well. Persist process-ownership/recovery evidence tied to lease ID and execution epoch, including preparation and recycling activity. Resolve a default-pool Ticket directory once at launch admission and persist its path before filesystem effects; retries must not create another directory.

Keep placement, directory affinity, current lease, and preparation evidence separate: a newly accepted Ticket may have pool placement but no affinity or lease while queued. Its first directory reservation fixes affinity; ending releases the lease, not affinity. A resumed Ticket may therefore have its original directory recorded but no lease while waiting for that directory. Preserve the existing name and assignment text in execution metadata while making the directory absent until allocation.

A placement-context version identifies an immutable snapshot of placement instructions and selectable pool IDs/descriptions, with the exact instruction revision retained for audit. Publish a new version when that semantic content changes; directory inventory, occupancy, eligibility, and worker-slot usage/limit changes do not change it. Acceptance validates the echoed version and selected pool against the current snapshot in the same transaction as Ticket creation. On a stale-context refusal, the main Session reads the refreshed context and retries acceptance for the still-undecided candidate through the existing tool; this is not a second placement phase for an accepted Ticket. Well-formed replays of accepted requests return the original result before checking current versions or pool existence.

Recovery clearance is not inferred from the lease's lifecycle state. Before restoring managed Sessions or dispatching effects after restart, fence all prior-epoch unreleased leases. Clear a fence only after verified quiescence of the old execution range and reconciliation of interrupted filesystem effects; record the evidence and new execution epoch atomically. Quarantine keeps the lease and affinity intact and holds no worker slot. Old-epoch callbacks cannot clear that fence or mutate later ownership.

## Default-pool creation is not inventory reuse

`default` bypasses fixed-inventory eligibility rules. It does not wait for a reusable directory, external Session presence clearance, Git cleanliness, or the corresponding observation services. The main Session may remain displayed or running in the state directory while default-pool Tickets execute beneath its `work` directory. This exception applies to the dedicated directory's lifecycle, not only to the reservation transaction; reapplying the same inventory gate during preparation or the first worker turn would undo it.

At first reservation, choose a nonexistent path that is not already registered or reserved. If the naming scheme collides with an existing path, leave that path untouched and disambiguate before committing affinity. After commit, create only at the persisted path with non-clobbering creation semantics; an unexpected path appearing before creation is a filesystem conflict to reconcile, not permission to adopt its contents or allocate a replacement. Retries and resumption use the same committed path. A resumed default-pool Ticket may retain its own uncommitted work; no clean-for-reuse gate or destructive recycling is needed to make a directory available to a different Ticket.

Default-pool directories remain dedicated, not externally shared workspaces or reusable inventory. The occupancy exemption does not provide concurrent-use safety for someone independently working inside one; such sharing is outside this policy. Lease ownership, Git working-tree exclusivity, worker limits, preparation verification, credential checks, preservation of unexpected contents, and process-quiescence/recovery requirements remain in force. An invalid preparation that borrows an ancestor's checkout must fail rather than masquerade as an independent new workspace.

## Git working-tree exclusivity

Resolve each existing Git directory's canonical working-tree root and worktree-specific metadata before reservation. Persist the root claim in the same transaction as the directory lease and affinity; constrain both canonical roots and verified worktree-specific metadata identities against duplicate unreleased owners. For example, registrations at `/repo/ui` and `/repo/api` share the resource `/repo` and can be leased only one at a time, even while the working tree is clean. They may coexist in inventory; a resource conflict makes both unavailable to other owners until safe release. Separate linked worktrees retain distinct resources despite sharing object storage/common metadata.

Hold the claim for the complete unreleased lease lifecycle, including idle/waiting periods and recovery fences, not just while Git commands run. No worker slot is held merely while waiting for a working-tree resource. Release the claim atomically with the directory lease, retain its history, and wake queues for every directory/pool sharing that root, not only the released directory ID. Recovery fences cover all paths resolving to a claimed root. Directory identity and Git resource identity remain separate; resolving a shared root does not change a Ticket's directory affinity.

Preparation that will create a Git working tree must declare and reserve its intended canonical root before any filesystem effect. For `default`, this is the fresh dedicated path, never an inherited parent working tree. Verify the resulting root and worktree-specific metadata before executing a worker; confirm a genuinely non-Git directory when no checkout is prepared, and remove an unused prospective Git claim only after that confirmation. Do not check out, reset, or otherwise prepare an ancestor's working-tree contents, index, or HEAD while creating the new workspace. A supported `git worktree add` hook may use the source repository's shared metadata to create the separate claimed worktree; that is not reuse of the source working tree. If preparation or an external change alters an existing root/metadata identity, fence use and reconcile ownership before further Git mutation; do not silently attach to another owner's resource. Recheck identity before preparation, execution admission, and recycling in both policies.

## External Session occupancy (fixed inventory only)

The rules in this section apply to fixed-inventory directories, not `default`. Directory leases cover superagent ownership; they do not account for unrelated DSH Sessions. Maintain a separate runtime occupancy view keyed by canonical workspace identity, with `clear`, `occupied`, or `unknown` status, an observation revision, and operator-visible blocking Session IDs/reasons. A directory is occupied if any unrelated Session is running, has an open user view, or still owns executing jobs/descendants. Only exclude Sessions positively identified as the requesting Ticket's own authorized execution range; a name prefix or being another superagent Session is insufficient.

“Open” means a Session is currently displayed in at least one live client's Session view, not merely persisted, loaded on the server, listed in a sidebar, read through an API, or retained in client memory behind a different global panel. Aggregate across browser tabs, windows, and clients: loss of browser/window keyboard focus does not close a displayed Session view, and closing one view does not clear another. Keep running status and view presence independent; finishing a turn does not free a directory while a user view remains open, and closing a view does not free it while work is running. Disconnect/reconnect, missed events, and Runtime startup must not fabricate a `clear` result; uncertain presence stays `unknown` until reconciled.

Resolve symlinks and compare directory boundaries, including overlapping ancestor/descendant workspaces, not just equal path strings or textual prefixes. Also compare resolved Git working-tree resources: an external Session in `/repo/ui` occupies the shared working tree for a fixed-inventory directory at `/repo/api`. Distinct linked worktrees are not conflated merely because their common Git directory matches. Re-evaluate occupancy when a Session changes its workspace or Git identity changes. Registering a directory in a pool does not take ownership from unrelated Sessions or make their occupancy disappear.

Observe and recheck occupancy at reservation and before managed filesystem work/turn admission. This is runtime state, not a database-only constraint: implement an admission protocol that serializes relevant Session-start, workspace-change, and view-open transitions with superagent reservation/use, or explicitly fence and await quiescence of superagent activity before a conflicting transition is admitted. Polling once before a lease transaction cannot establish this guarantee. If an external occupant appears after reservation, retain the lease/affinity, fence new managed work, stop and await the Ticket's managed activity, and defer preparation/recycling until the conflict clears and the workspace is revalidated. Do not kill external work, close user views, release ownership prematurely, or substitute a different directory after affinity has been committed.

Occupancy and presence are Executor/operator concerns, not main-Session placement input. They do not change the placement-context version, invalidate an accepted pool choice, or authorize pool switching. Distinguish a confirmed occupant (ordinary waiting) from unavailable/unreconciled observation (a safety diagnostic).

## Git cleanliness at fixed-inventory acquisition and reuse

The cleanliness gate in this section applies only to fixed-inventory directories. `default` creates a fresh dedicated directory and does not use this gate, including when resuming its own retained workspace. Git working-tree identity and exclusive claims are separate from cleanliness and still apply to both policies.

Use read-only Git inspection to resolve the actual working-tree root and worktree-specific Git metadata; a linked worktree may have a `.git` file rather than a directory. A directory inside a larger working tree must check that whole working tree, not just a path-filtered subset. A not-yet-created or confirmed non-Git directory is not rejected merely for lacking Git metadata; existing filesystem/preparation rules still apply. A malformed/inaccessible repository, invalid worktree metadata, bare repository without a usable working tree, or failed/timed-out probe is not a clean execution checkout.

For Git working trees, use machine-readable status with all untracked files and submodule changes included, independent of user display/hide settings. Staged changes, unstaged modifications/deletions, untracked files/directories, conflicts, or dirty submodules make the directory ineligible. Detect unfinished merge/rebase/cherry-pick/revert operations separately, including cases where status has no changed paths. Ignored outputs alone do not make Git status dirty; Git cleanliness does not authorize deleting those outputs or imply that branch identity, artifact preservation, and recycling checks have passed.

Check before selecting a first-reservation candidate or reacquiring an affinity directory, then recheck under the reservation/admission protocol immediately before the new lease's preparation can modify contents. If the workspace changes after reservation, retain its lease/affinity and surface a remediation condition rather than overwriting changes, falsely marking preparation complete, or substituting another directory. A pre-reservation rejection does not acquire a lease or advance LRU usage. Neither dirty status nor a failed probe changes the semantic placement-context version or sends placement back to the main Session.

Do not apply the clean-before-acquisition predicate to every turn/tool call under the same unreleased lease: preparation and implementation can legitimately create Ticket-owned changes. A retry or Runtime recovery retaining that lease preserves those changes, subject to existing process-quiescence and ownership checks. Before releasing a Git workspace for subsequent acquisition, preserve required Ticket state, complete authorized recycling, and verify a clean working tree; otherwise retain the lease and surface the specific issue. No eligibility probe may run destructive repair or manufacture a commit/stash to pass the check. Normal authorized Ticket work or separately authorized preservation/recycling may resolve changes, but unexpected changes must never be discarded automatically.

## Rule-driven routing and execution flow

```text
Incoming request → ingestion/admission → candidate delivered to main Session
                                                   ↓
Main Session reads: candidate requirements + versioned placement context (rules + pool IDs/descriptions)
                                                   ↓
Explicit:  orchestrator_route(kind=accept, placement={poolId, reason, contextVersion})
Proactive: orchestrator_eval_decide(decision=accept, placement={poolId, reason, contextVersion})
                                                   ↓
Engine transaction: already accepted → return original result, with no new effects
                    otherwise validate authorization/context version/pool
                   → persist Ticket with selection and exact versions → enqueue launch via Effects
                                                   ↓
Executor scheduler admits a Ticket without directory affinity when a worker slot is available:
  fixed-inventory pool: select the least recently used directory eligible for lease acquisition
  default pool: choose a fresh Ticket-specific path; do not apply inventory eligibility gates
                                                   ↓
Executor atomically rechecks admission/ownership/recovery (and fixed-inventory eligibility where applicable)
  → commits reservation: lease/affinity/Git working-tree claims/preparation intent
                                                   ↓
Durable effect creates directory if needed → prepares contents → verifies Git identity/claims and completion
                                                   ↓
Sessions creates/resolves Executor Session → Executor delivers assignment via Sessions
```

Example explicit acceptance item (inside the existing routing tool's `decisions` array):

```json
{
  "kind": "accept",
  "trigger_id": "...",
  "title": "Fix login layout",
  "worktree_name": "fix-login-layout",
  "acknowledgement": "I'll fix the login layout.",
  "placement": {
    "poolId": "frontend",
    "reason": "UI work belongs in the frontend pool.",
    "contextVersion": "placement-context-42"
  }
}
```

Set `placement.poolId` to `"default"` when no operator-configured pool is selected under the placement instructions, with `placement.reason` explaining that selection and `placement.contextVersion` echoing the context read. The main Session still selects only a pool; the Executor creates the default pool's Ticket-specific directory. Proactive acceptance carries the same nested `placement` object through its existing assessment tool. There is no separate `kind: 'new'` placement.

Example operator instructions:

```text
Use the frontend pool for UI work.
Use the backend pool for server implementation work.
If a request spans multiple areas, choose the pool matching its primary change.
If no operator-configured pool is selected under these rules, use the default pool.
Do not change pools based on directory eligibility or worker-slot availability.
```

No `wait` placement is needed: waiting for directory eligibility or a worker slot is an Executor-managed queue state, not a placement decision. Acceptance and pool placement are one durable decision in the existing routing/assessment path. Missing or invalid placement refuses acceptance without consuming the candidate or creating a partially configured Ticket. A known fixed-inventory pool with no directory eligible for lease acquisition remains a valid placement target; the accepted Ticket waits in its queue.

Use existing candidate delivery to trigger the main-session acceptance decision; do not introduce a second initial-placement notification loop. If placement instructions or pool descriptions change, refresh the routing context for future decisions without automatically replacing recorded selections. Directory-lease releases, worker-slot changes, and reservation races wake the Executor scheduler only, without another main-Session decision. Resumption does not re-route placement: after the Engine's normal resumption authorization checks, the Executor queues acquisition of the Ticket's original directory. If another Ticket leases it, wait for that lease to end and recycling to finish, then reacquire and restore the original Ticket's checkout. For a Ticket that ended before its first directory reservation, retain its selected pool and perform first directory reservation normally.

## Completion criteria

- The built-in `default` execution directory pool always exists with the per-Ticket creation policy and the default-pool root. The operator may define additional fixed-inventory pools and writes semantic pool-selection instructions.
- Settings → Execution provides working add/edit/remove UI for operator-configured pools and directory registrations, including editable pool descriptions, stable IDs, path/membership validation, confirmations, revision-aware saves, and actionable lifecycle restrictions. The backend enforces the same rules; removal never deletes filesystem contents or erases retained affinity/history. The built-in `default` pool keeps its identity/policy and offers only its supported description/root edits.
- The main Session records pool placement using Ticket requirements, operator rules, and pool IDs/descriptions. Its target is a pool ID; reason and context version are required metadata. It chooses `default` when no operator-configured pool is selected under those rules, never an individual directory or allocation policy and never based on directory eligibility or worker-slot availability. New acceptances reject stale versions atomically; replays return their original selection and audit versions.
- The Engine records pool placement through the Store and queues execution through Effects without assigning newly accepted Tickets a pathname. At first launch admission, the Executor selects an eligible fixed-inventory directory by LRU or chooses a fresh default-pool path, commits the directory lease/affinity/Git-working-tree claims/preparation intent, and only then creates the directory if needed and prepares workspace contents. A fixed-inventory Ticket with no eligible directory waits without fallback or further main-Session decisions.
- `default` always creates a fresh dedicated directory at first launch and never applies fixed-inventory eligibility rules, including external Session occupancy and Git-clean-for-reuse gates. The main Session running or displayed at the state directory, dirty inventory, and missing inventory-observation support do not block default-pool work. Retries/resumption keep the committed directory; authorization, worker limits, exclusive ownership, preparation/filesystem correctness, preservation, and recovery safeguards remain in force.
- Every executing Ticket owns an active, durable lease for its actual Session workspace and the resolved Git working-tree resource, if any; queued Tickets may have a selection but no lease.
- No fixed-inventory directory is used by the superagent while an unrelated Session on an overlapping workspace or shared Git working tree is running or displayed in any live user Session view, or while external background work remains. Occupancy must be positively reconciled, not inferred from missing lease rows or unloaded Sessions. Multi-client presence/admission integration, post-reservation conflict handling, operator diagnostics, and no-slot waiting are implemented and tested; incomplete observation fails closed for fixed inventory, not globally for `default`.
- Fixed-inventory Git directories must be verified clean before a new lease is acquired or a released lease is reacquired; dirty, unfinished, or unknown Git state is ineligible. Check the full working tree, including untracked/submodule changes, without destructive repair. The Ticket may make normal changes under its own unreleased lease; safe preservation/recycling must restore cleanliness before fixed-inventory reuse. Dedicated default-pool directories retain their own contents without this reuse gate.
- A canonical directory has no more than one unreleased owner, and a resolved Git working-tree root has no more than one owning directory lease across all pools. Sibling subdirectories of one working tree serialize; distinct linked worktrees remain independent. Root claims are durable, acquired/released atomically with directory leases, preserved through recovery, and verified before preparation/execution/recycling. Default preparation creates its own independent checkout/worktree rather than borrowing an ancestor's.
- Retries and restarts preserve selections and ownership; verified process quiescence and completed recycling are required before reuse. Hard-crash recovery includes active leases and fails closed to quarantine when supervisor/process-owner evidence is unavailable; lost in-memory job records never establish safety.
- Ended Tickets resume only in their original directory, waiting for its lease/recycling if necessary, without another placement decision or directory substitution. Directory affinity persists after lease release, and intervening use requires safe checkout restoration. A reservation whose creation has not started may be created at its pinned path; interrupted preparation is reconciled using its durable intent/start/completion records.
- Acceptance uses the same required `placement: { poolId, reason, contextVersion }` object in both existing routing and assessment tools; there is no separate initial dispatch tool or normal awaiting-placement phase.
- The glossary is used consistently in code, tools, prompts, panel labels, and documentation. Pool placement, directory reservation, filesystem creation, workspace preparation, directory-lease release, and freeing a worker slot are distinct operations.
- All documentation updates in step 8 ship with the implementation, including accurate tool/resource examples and operator recovery instructions. Documentation and implementation tests pass together; the feature is not complete with stale docs. They cover semantic pool selection independent of directory/worker-slot scheduling, durable LRU reservations, exact-directory resumption queues, both allocation policies, and the complete lease lifecycle.
